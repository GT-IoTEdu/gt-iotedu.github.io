Purpose

The same concept shows up today under different names: dispositivo and aparelho, Detection engines, IDS sensors and Real-time IDS/IPS. And one name points to different things: gateway has four meanings, and liberar means both approve and unblock. This glossary sets one term per concept, in Portuguese and English. For each term it says what it is, what it does inside IoTEdu and how it appears in the code, and lists the words to avoid.

Rules

  1. On screen, the glossary term. If a concept is not here, it goes into the glossary before it goes on screen.
  2. No internal values on screen. Values such as mixed, MANAGER, gwapi, manual_allowed, SUPERUSER_ACCESS and global are not shown to people using the dashboard; the full list is in Internal values that stay off the screen.
  3. One meaning per word. If a word already has a meaning here, don't reuse it for another. Example: Activity is the audit screen, so the time a device was last seen is Last seen, not Last activity.
  4. The same pt/en pair everywhere. The i18n catalog uses the pair from this table, and the catalog test already requires the same translation for the same key.
  5. In technical docs, the technical name goes in parentheses. Example: "Authorized group (nft set manual_allowed)". The technical name explains the term; it does not replace it.
  6. Issues and PRs use these terms. Whoever reports can use any word; the title and the "Situação no código" section use the glossary term.

Status column legend: in use = already the interface or code term; decided = settled on 2026-10-16, with the interface and docs still to be updated; open = no answer yet.

1 Project and organization

#IoTEdu IoTEdu

What it is. A platform for managing and protecting institutional IoT networks. A user registers a device by MAC and gets a fixed address on the IoT network. The network manager allows or blocks access. The IDS watch the traffic and can block the device on their own. Everything runs on a single Linux host with Docker Compose. Spelling. Always IoTEdu. Avoid IOTEDU, IoT-EDU and Iotedu. The API-IoT-EDU in ids-agent/ids_signing.py is a leftover.

#GT-IoTEdu IoTEdu working group

What it is. The working group and the GitHub organization. Repositories whose name starts with an underscore (_backend, _dhcp, …) are stack components; the others predate the stack or are unrelated to it. Avoid translating it halfway ("GT IoTEdu" in one place and "WG" in another). In English use "IoTEdu working group" or keep "GT-IoTEdu".

#Stack Stack

What it is. The umbrella repository iotedu-stack. It holds docker-compose.yml, .env.example, the scripts and the docs, and includes each component as a submodule. In the system. A stack version is a reproducible combination of components, because each submodule is pinned to a commit (gitlink).

#Component Componente

What it is. A part of the stack with its own repository: backend, frontend, idp, bootstrap, gateway, dhcp, firewall, clients, monitoring, ids, ids-agent, fingerprint and attack. Not to be confused with a service (a compose container). A component can have several services; ids has three, for example.

#Submodule, gitlink Submódulo, gitlink

What it is. The submodule is the component's directory inside the stack. The gitlink is the commit of it that the stack uses. In the system. A merge to a component's main reaches a deployment only after the gitlink is updated in the stack and someone runs implanta.sh atualizar.

#Deployment Instalação

What it is. A stack running for one institution. There are two today: UNIPAMPA (app-unipampa.iotedu.org) and UFRGS (iotedu.ufrgs.br). Avoid "instance" and "environment" with the same meaning. Environment is for lab vs. production.

#Lab mode Modo lab

What it is. A deployment without a physical network: LAN_PARENT_IFACE empty, the IoT network on the internal bridge br-gateway-lan, *.iotedu.localtest.me domains and Caddy's local CA. Opposite: physical mode (a real VLAN via macvlan), which is how institutions run.

#Demo Demo

What it is. The demonstration data created by db-init and the realm: the default unit "Demo IoTEdu"/"Lab", with an SSID and password (DEMO_WIFI_*), the accounts superuser@, admin@ and user1..4@ (each with its role when SEED_DEMO_PESSOAS=true), client1 and client2, and the DEMO_IP_RANGE_* ranges. implanta.sh demo completes the set with the stack running: three more devices, allowing, an incident with an automatic block of client2 and a Pending appeal (#84). Note. In production, DEMO_IP_RANGE_* is the unit's real reservation range, despite the name.

#MVP MVP

What it is. Not a defined stage of the stack. It appears only in the old repository name mvpv1-snapshot and in issues such as "what must be ready for the demo". To decide whether the term becomes an official milestone (with a date and scope) or leaves the vocabulary.

#iotedu-dockerized iotedu-dockerized

What it is. The previous monolithic repository, frozen in October 2026. References to it (for example, docs/pt-br/hardware-baseline.md and app/backend/... paths) are historical.

#UNIPAMPA, UFRGS, RNP UNIPAMPA, UFRGS, RNP

What they are. The two institutions with a deployment (UNIPAMPA: VLAN 915, SSID IoTEdu, gateway at 10.2.226.2) and Brazil's National Research and Education Network, which runs the CAFe federation and registers service providers (SPs).

2 People, roles and units

#Institution Instituição

What it is. The organization: the university or institute (UNIPAMPA, UFRGS). In the system. One deployment serves one institution. In CAFe, the home institution (instituição de origem) is the institution whose IdP authenticates the person. Note. In the code, the institutions table and the institution_id field represent the unit, not the institution. It's a historical name: keep it in the code and say unit on screen.

#Unit Unidade decided

What it is. The network slice IoTEdu manages: one institutions row, with a name and a city. What it does in the system. Each unit has:

  • its own fixed IP range (ip_range_start–ip_range_end);
  • its own gateway (gateway_backend, gwapi_base_url);
  • the wireless network (wifi_ssid, wifi_password);
  • the Allow devices on registration? option;
  • its managers, alert agents and devices.

Every record (device, alert, appeal) belongs to a unit, and a network manager only sees their own. On first sign-in, the user picks the unit (PUT /api/auth/me/institution); after that, only the superuser can change it. Avoid campus and campuses, and don't use institution for the unit (the map currently says "Institution {name}"). In English, don't alternate unit and institution. Open question: is a unit always a campus? Or can there be more than one unit on the same campus (a building, a lab)?

#Short name Sigla

What it is. The unit's abbreviation (e.g. UNIPAMPA-AL). Use short name in English; avoid acronym. In the system. It isn't stored yet: the dashboard uses sigla if the backend sends it and otherwise joins the initials of up to four words of the name ("Demo IoTEdu" → DI).

#User Usuário (USER)

What it is. Someone who registers and follows their own devices. What they can do in the system:

  • register devices;
  • see only the devices they own;
  • appeal a block.

What they cannot do:

  • allow or block;
  • remove a blocked device;
  • see the network map;
  • see which probe caused a block or incident (#49).

Avoid "regular user" on screen.

#Network manager Gestor de rede (ADMIN) decided

What it is. The person who runs the IoT network of one unit. What they do in the system:

  • allow, block and remove the unit's devices;
  • handle incidents and review appeals;
  • edit My network (range, wireless network, allow on registration);
  • see the unit's network map.

State of the code. The enum has only USER, ADMIN and SUPERUSER. However:

  • User.is_manager() checks ADMIN, and is_admin() checks SUPERUSER;
  • the guards accept the string "MANAGER";
  • the frontend shows MANAGER as "Network manager" and ADMIN as "Unit administrator" (nav.ts:82-83);
  • Help lists only three levels.

Decided. Three roles, one name each: User, Network manager (ADMIN) and Superuser. MANAGER and "Unit administrator" are removed from the code and the screen.

#Superuser Superusuário (SUPERUSER)

What it is. The administrator of the whole deployment. What they do in the system:

  • act on any unit (by passing institution_id);
  • create units;
  • change users' roles and set each unit's managers;
  • manage alert agents and sign-in methods.

The email in SUPERUSER_ACCESS is always a superuser and can sign in through superuser access (/login/admin) even when the sign-in method is switched off. Avoid "global administrator" and "IoTEdu administrator".

#Owner Responsável

What it is. The user linked to a device (user_device_assignments). Whoever registers a device becomes its owner automatically. What it does in the system. Decides who sees the device and who can appeal its block. A device can have more than one owner, or none ("No owner"). Open problem: #23.

#Role Papel

What it is. A person's access level (User, Network manager, Superuser). Avoid using Profile for role ("Role:" in the menu is fine; "Profile" is the My profile screen). In Portuguese, Perfil is used for both, which this rule fixes. A service's "role" in System health is called Function / Função.

3 Device and lifecycle

#Device Dispositivo decided

What it is. Any equipment registered by MAC that gets a fixed IP on the IoT network: a board (ESP32, Raspberry Pi), a sensor, a lamp, a phone, a laptop. In the code. The table is dhcp_static_mappings (DhcpStaticMapping), because technically a device is a DHCP reservation. The foreign keys are dhcp_mapping_id and device_id. Avoid (pt) aparelho: the catalogs currently have ~83 "aparelho" against ~114 "dispositivo", sometimes in the same dialog. In English it is always device. Decided: dispositivo in Portuguese (more technical, matches English).

#Device type Tipo de dispositivo

What it is. The category chosen at registration: phone, sensor, camera, LoRa gateway, etc. (#59 proposes more types and brand/model fields). Note. The "LoRa gateway" type is a device on the network, not the IoTEdu gateway.

#MAC address MAC

What it is. The physical address of the network interface. It identifies the device in IoTEdu. What it does in the system. It is the key of the DHCP reservation: the same MAC always gets the same IP. The form accepts any punctuation and normalizes it to XX:XX:XX:XX:XX:XX.

#Randomized MAC MAC aleatório

What it is. The address phones and laptops invent for each network ("private address"). In the system. The registered MAC must be the one the device uses on this network; otherwise the reservation never matches and the device stays on a pool IP.

#Identifier Identificador

What it is. The short device name entered at registration (e.g. sensor-bench-3). In the code. cid (client ID), validated as a hostname.

#Register, registration Cadastrar, cadastro decided

What it is. Adding a device to IoTEdu. What it does in the system. When a device is registered:

  1. the system picks the IP (automatically, the lowest free one in the unit's range, or manually);
  2. creates the reservation on the DHCP server through the gateway API;
  3. saves the device in the database;
  4. links whoever registered it as owner;
  5. sets the initial status (Awaiting approval, or Allowed if the unit allows on registration).

The route is POST /api/devices/dhcp/save, for every role. A User doesn't pick the IP: the server takes the lowest free one in the range. There is also POST /api/devices/dhcp/static_mapping (manager), which only creates the reservation and isn't used by the screen. Avoid (pt) alternating registrar and cadastrar. In English, Register.

#Self-registration Autocadastro

What it is. Registration helped by the Fingerprint. What it does in the system. The system opens a listening window (POST /api/devices/dhcp/fingerprint/observar) and lists the devices that just requested DHCP. The person picks theirs, and the form comes pre-filled with MAC, name, type and manufacturer. The device stores fingerprint_sha256. The fixed IP always comes from the unit's range, never from the IP seen in the capture. Related: #17.

#Access status Situação de acesso

What it is. What the device may do on the network. It has three values and is independent of presence (Online / Offline). In the code. status_acesso = LIBERADO | BLOQUEADO | AGUARDANDO (status_acesso_service.py). The decision order is: is_blocked, then IP in the Blocked group, then IP in the Authorized group, then firewall rules that cite an alias holding the IP, otherwise Awaiting.

Status Português What the firewall lets through How a device gets here
Awaiting approval Aguardando liberação only DNS, HTTP/HTTPS (80/443) and ping registration with allow on registration off
Allowed Liberado everything a manager allows it, or registration with allow on registration on
Blocked Bloqueado nothing a manager blocks it, or an automatic block

Note. A device Awaiting approval can already open websites, because 80/443 pass. What allowing changes is the rest: MQTT, NTP, SSH and other ports. Decided. Badge "Pending" → "Awaiting approval", replacing "Pending" and "Allowance pending", so that Pending is used only for appeals.

#Allow Liberar decided

What it is. Giving full network access. What it does in the system. Puts the device's IP in the firewall's Authorized group. If the device was blocked, it also removes the IP from Blocked, clears the reason and makes the IDS "forget" the block (esquecer_bloqueio_dos_ids), so a new attack blocks it again. The result is always Allowed, whether the device was Awaiting approval or Blocked. The route is POST /api/devices/devices/{id}/unblock. The #24 case (allowing after a block without putting the IP in Authorized) is already fixed in the code; the issue awaits an on-screen test. Avoid approve, authorize, unblock, release and the noun allowance on screen. The technical group name (Authorized) stays in the docs. Note. "Release IP" (DELETE /api/devices/ip-assignment/release/{ip}) is something else: it returns an IP to the range. On screen, Release IP / Devolver IP.

#Block Bloquear, bloqueio

What it is. Cutting all of the device's network access. What it does in the system. Sets is_blocked=True and the block reason (reason). Removes the IP from Authorized and adds it to Blocked; the Blocked rule comes before the Authorized one, so the block always wins. It also records a row in the appeals table (blocking_feedback_history). There are two kinds:

  • Manual block (Bloqueio manual): done by a network manager or the superuser.
  • Automatic block (Bloqueio automático): done by the backend from IDS alerts (section 5).

Note. The block is by IP. A blocked pool IP stays blocked for the next device that gets it (challenge 19 in challenges). Avoid suspend for devices; suspend is for user accounts.

#Allow devices on registration? Dispositivo já nasce liberado?

What it is. A unit option in My network (institutions.auto_liberar_dispositivos, #21). What it does in the system. When on, registration puts the IP straight into Authorized, and the device starts as Allowed without a manager in the loop. Turning it on allows the whole Awaiting approval queue at once, after a confirmation. When off (the default), every device starts Awaiting approval. Note. With the option on, the IDS are the only barrier. One English text. The same control currently appears as "Allowed on registration?" and "Allow devices on registration?".

#Remove Remover

What it is. Deleting the device from IoTEdu. What it does in the system. Deletes the DHCP reservation and the owner links. Removes the IP from both the Authorized and Blocked groups, so the next device with that IP doesn't inherit the access. Keeps the appeal history, with the removed device's name, MAC and IP. A user cannot remove a blocked device. Avoid delete on screen.

#Presence: Online / Offline Presença: Conectado / Desconectado

What it is. Whether the device is on the network right now. It is independent of access status: a device can be Allowed and Offline. What it does in the system. The gateway computes presence from three signals:

  1. the ARP table (ip neigh, state REACHABLE);
  2. an active ping to the reserved IPs;
  3. the traffic measured in conntrack (packets per second).

A confirmed IP stays online for PRESENCE_GRACE_S (30 s). The screen re-reads presence every 15 s; the backend also polls the gateway every PRESENCE_POLL_INTERVAL_S (60 s) to record Last seen even when nobody is looking. Related: #12. It is not the DHCP lease (that old heuristic was dropped). On screen. Online / Offline in English, Conectado / Desconectado in Portuguese. Avoid active/inactive and "Allowed, inactive" (use "Allowed, offline").

#Last seen Visto por último decided

What it is. The last moment presence confirmed the device (last_seen_at). Empty means Never seen (Nunca visto). It is not the registration date or the last change (updated_at). Related: #5 and #13. Avoid "Last activity", which collides with the Activity screen.

#Joined on Entrada na rede decided

What it is. The date the device was registered on the network (created_at). #46 asks for it to appear on screen. Avoid "Registered on" and "Join date" with different meanings.

4 Network and infrastructure

This section says what each piece is and what it does inside IoTEdu. In short, three containers share a single network namespace and together are the IoT network's router:

            Internet / institution network
                         │  (WAN, NAT)
   ┌─────────────────────┴──────────────────────┐
   │ IoTEdu gateway (one network namespace)     │
   │  ├─ iotedu-gateway  → Gateway API (GWAPI), routing, presence
   │  ├─ iotedu-firewall → nftables: Authorized/Blocked groups, NAT
   │  └─ iotedu-dhcp     → Kea: reservations and leases
   └─────────────────────┬──────────────────────┘
                         │  (LAN = IoT network, the unit's VLAN)
          devices  ·  IDS listening on this interface

The backend talks only to the gateway API (GWAPI_INTERNAL_URL, http://iotedu-gateway:8080), which forwards requests to the firewall and to DHCP.

#IoT network Rede IoT decided

What it is. The segment where the devices live: the VLAN the institution's IT provided (at UNIPAMPA, VLAN 915, 10.2.226.0/24) or, in the lab, the br-gateway-lan bridge. What it does in the system. The IoTEdu gateway is the router and DHCP server of this segment. It is the stack's LAN: LAN_CIDR, LAN_IP and LAN_PARENT_IFACE in .env. On screen, IoT network. Use LAN only in technical docs. There is no "IoT network" separate from the LAN: they are the same segment.

#WAN WAN

What it is. The gateway's outbound side: the Docker network gateway_wan (10.89.0.0/24). What it does in the system. Device traffic leaves through it with NAT. It is also how the backend reaches the gateway API. A technical-docs term; it doesn't go on screen.

#Wireless network (SSID) Rede sem fio (SSID)

What it is. The name (SSID) and password of the IoT network's Wi-Fi, stored on the unit (wifi_ssid, wifi_password). What it does in the system. It is information only: IoTEdu does not configure the access point. The value is shown at registration so the user knows which network to connect the device to (#15, #39).

#Access point Ponto de acesso

What it is. The institution's Wi-Fi equipment that broadcasts the IoT network's SSID. It is outside the stack. In the system. It only carries devices to the VLAN; the IoTEdu gateway hands out IPs and decides access.

#VLAN router Roteador da VLAN

What it is. The router IT already has on the segment (at UNIPAMPA, 10.2.226.1). What it does in the system. Nothing on the devices' path, which goes out through the IoTEdu gateway. It must be in IDS_AUTOBLOCK_WHITELIST, so a burst of alerts doesn't block it. Docker requires its address as LAN_DOCKER_GATEWAY.

#Gateway (network sense) Gateway (sentido de rede)

What it is. In general, a segment's default router, which connects the network to other networks. In IoTEdu. For the devices, the default gateway is the IoTEdu gateway: DHCP hands out routers = LAN_IP, and traffic leaves through it with NAT. The term is correct in the network sense. The problem in #44 is that the interface uses "Gateway" for something else: the control role ("who applies allows and blocks") and the API + firewall + DHCP set shown as a single item.

#IoTEdu gateway Gateway IoTEdu decided (#44)

What it is. The set of three compose services that share one network namespace (iotedu-gateway, iotedu-dhcp, iotedu-firewall; containers iotedu-gw-gateway, iotedu-gw-dhcp, iotedu-gw-firewall), deployed per unit. It replaces pfSense. What it does in the system:

  1. routes the IoT network outward, with NAT;
  2. filters traffic (firewall);
  3. hands out addresses (DHCP);
  4. measures device presence;
  5. exposes the API the backend uses for all of this.

It has its own IP on the VLAN (LAN_IP, at UNIPAMPA 10.2.226.2). Operational caution. Recreating iotedu-gateway recreates the other two and takes down DHCP and routing on the IoT network. Do it only through implanta.sh recriar-tudo. Decided (#44). The set stays IoTEdu gateway, because it really is the IoT network's gateway, and its parts get their own names:

  • in System health, Firewall, DHCP server and Gateway API become separate items (#40);
  • on screen, the description stops being "who applies allows and blocks" and becomes "router of the IoT network: firewall, DHCP and presence".

Access controller was rejected: it would call "controller" a piece that also routes and does NAT.

Avoid "Network gateway (firewall + DHCP)", "gateway" for the firewall or DHCP alone, and "the gateway's block list" (the correct form is "the firewall's Blocked group").

#Gateway API (GWAPI) API do gateway (GWAPI) decided

What it is. The Flask process in the iotedu-gateway service (container iotedu-gw-gateway), on port 8080. It is the IoTEdu gateway's only entry point. What it does in the system:

  • authenticates the backend with HTTP Basic, using the unit's ADMIN_USER / ADMIN_PASSWORD;
  • forwards /dhcp/* to the DHCP API (127.0.0.1:8081) and /firewall/* to the firewall API (127.0.0.1:8082);
  • answers /network/presence (presence);
  • answers /health (health of DHCP and firewall, with each one's version, plus its own; 503 if a part fails) and /health/live;
  • serves two HTML diagnostic pages of its own, behind a login page.

The backend stores its address in institutions.gwapi_base_url. On screen. The internal address (http://iotedu-gateway:8080) is not shown to the manager (#66). gwapi is not screen text. Note. FW_API_PORT is the gateway API port, not the firewall's. The FW_ prefix is left over from before the split.

#pfSense pfSense

What it is. The external firewall/DHCP that IoTEdu used before. It is still an option per unit (gateway_backend = pfsense | gwapi). In the code. The GWAPI client imitates pfSense's alias vocabulary (cadastrar_alias_pfsense, pf_id) even when the unit uses GWAPI; pf_id 1 and 2 are constants, not real IDs. On screen, show "pfSense (legacy)" only to the superuser.

#Firewall Firewall

What it is. The iotedu-firewall service (container iotedu-gw-firewall): nftables plus an internal API (127.0.0.1:8082). Its state is stored as JSON on the iotedu_gateway_state volume. What it does in the system. Decides what each IP on the IoT network may reach outside it:

  • Default policy: deny (default deny). input and forward use policy drop; the lan_to_wan chain ends by dropping.
  • Initial rules: DNS (53), HTTP (80), HTTPS (443) and ICMP pass for everyone. That is why Awaiting approval devices can already browse.
  • System rules: drop-manual-blocked drops everything from Blocked; allow-manual-allowed accepts everything from Authorized. The drop comes first, so the block wins.
  • NAT (masquerade) of LAN_CIDR out the WAN.

Allowing and blocking don't create rules: they only add or remove the IP (/32) from the groups.

#Authorized group / Blocked group Grupo Autorizados / grupo Bloqueados decided

What it is. The two IP sets that define access status. The same group has four names, one per layer:

Layer Allowed Blocked
nftables (firewall) set manual_allowed set manual_blocked
Firewall API group manual_allowed group manual_blocked
Backend (pfSense-style alias) alias Autorizados alias Bloqueados
Backend (also accepted name) liberados bloqueados
Screen and docs "Autorizados" / "liberados" (#24) "Bloqueados" / "block list"

Decided. In the docs, Authorized group and Blocked group (grupo Autorizados / grupo Bloqueados), with the nft name in parentheses on first mention. On the user and manager screens, talk about the status (Allowed / Blocked), not the group. The names in the code and on the gateway don't change, because renaming would require migrating the alias in the database and on the gateway. The liberados spelling, accepted as a synonym, is not used in new text.

#Alias Alias

What it is. A named group of IPs, networks or ports per unit (pfsense_aliases), inherited from pfSense. The Aliases screen is in the Network menu. In the system. Authorized and Blocked are system aliases; the rest are free for the manager to use. Note. In the firewall API the same concept is called group and, in nftables, set.

#Firewall rule Regra (de firewall)

What it is. One line of the policy: source, destination, port, action (pass/block). Not to be confused with an IDS rule (signature, section 5). Always say "firewall rule" or "IDS rule".

#NAT NAT

What it is. Translating IoT network addresses to the host's address on the way out (masquerade). Devices use private IPs and go out with the IoTEdu server's IP.

#DHCP server Servidor DHCP

What it is. The iotedu-dhcp service (container iotedu-gw-dhcp): ISC Kea DHCPv4 plus the Kea Control Agent and an internal API (127.0.0.1:8081). What it does in the system. Gives devices an IP, the router (LAN_IP), DNS (DHCP_DNS) and domain (DHCP_DOMAIN). The API changes Kea's running configuration (config-set) and stores reservations in DHCP_RESERVATIONS_FILE. There can be only one DHCP server on the VLAN.

#Reservation Reserva

What it is. The fixed MAC ↔ IP binding on the DHCP server. Every registered device has one. What it does in the system. Ensures the device always gets the same IP, and that IP is the one that goes into the firewall groups. The device starts using the reserved IP only after it requests DHCP again (disconnect and reconnect). In the code. dhcp_static_mappings (pfSense: static mapping), gateway_reservation_id (UUID on GWAPI). Avoid "static mapping" on screen.

#Unit IP range Faixa de IPs da unidade

What it is. The interval the registered devices' fixed IPs come from (ip_range_start–ip_range_end; initially DEMO_IP_RANGE_*). Rule. It must be disjoint from the pool; otherwise the same IP can be leased and reserved at the same time (challenge 3). Related: #47.

#Dynamic pool Pool (dinâmico)

What it is. The range of temporary IPs for devices not yet registered (DHCP_POOL_START–DHCP_POOL_END). In the system. A pool device gets Awaiting approval access: only DNS, 80/443 and ping.

#Lease Concessão

What it is. DHCP's time-limited loan of an IP. Leases are in Kea's lease file (kea-leases4.csv, volume iotedu_gateway_leases). It is not presence: a valid lease doesn't mean the device is online.

#Shared network namespace Namespace de rede compartilhado

What it is. The firewall and DHCP run with network_mode: service:iotedu-gateway, that is, inside the gateway container's network: the same interfaces, the same IPs, the same 127.0.0.1. Consequence. The three form a group: recreating the gateway recreates the other two.

#Macvlan, VLAN NIC Macvlan, NIC da VLAN

What it is. The network mode in physical mode: the gateway joins the VLAN as if it were its own machine, with its own MAC, through the host NIC attached to the VLAN (LAN_PARENT_IFACE, at UNIPAMPA eno1). Note. In a VM, the hypervisor must allow promiscuous mode and MAC spoofing (challenge 2).

#Capture interface Interface de captura

What it is. The interface the IDS listen on (IDS_CAPTURE_IFACE): the VLAN NIC in production, br-gateway-lan in the lab. In the system. The IDS see the traffic because they listen on the IoT network's own interface. No mirror (SPAN) port is configured.

5 Detection: IDS, probes and rules

#IDS IDS (intrusion detection system)

What it is. A system that watches traffic and raises alerts when it matches an attack pattern. In IoTEdu it is the ids component, with three security probes. What it does in the system. It only detects. The IDS block nothing: the backend blocks, based on the alerts. That's why the "IPS" role doesn't apply, and "Real-time IDS/IPS" should come off the screen. On screen. IDS (plural the IDS) for the set.

#Security probe Sonda de segurança decided (#42)

What it is. Each of the three detection programs: Suricata, Snort and Zeek. What it does in the system. Each probe is a container (iotedu-ids-*, host network), listens on the capture interface, writes its own alert file and touches .engine_alive every 30 s. Today the same concept has five names: "Detection engines", "Motores de detecção", "Real-time IDS/IPS", "Engine: …" and "scanner". All of them become security probe / sonda de segurança. On screen, when the context is already security, probe / sonda is enough ("Probe: Suricata", "All probes"). The proper names (Suricata, Snort, Zeek) are always capitalized. In the code the old names stay: engine, engines_status, sensor_type and the /api/scanners/... routes.

Each probe's function, in operational language (replacing "Real-time IDS/IPS" and "Complementary"):

Probe How it detects On-screen function (en / pt)
Suricata signatures and rates (local rules + ET Open); writes fast.log Signature-based detection / Detecção por assinaturas
Snort (3) signatures and rates (local rules, port scan inspector); writes alert_fast.txt Signature-based detection / Detecção por assinaturas
Zeek behavior (scanning, DoS, exfiltration, DNS entropy, MQTT/CoAP/Zenoh); writes notice.log Traffic behavior analysis / Análise de comportamento do tráfego

#IDS rule, signature Regra de IDS, assinatura

What it is. A pattern a probe looks for in traffic. In Snort and Suricata, a .rules line (alert … (msg; sid; rev; priority)); in Zeek, a detector script. In the system. The copy that runs is the one in ids/rules/ (mounted read-only). The copy in implementation/ must be identical, and scripts/verifica-ids-regras.sh checks that. On screen. Signature (Assinatura) is the description of what was detected (the msg).

#SID SID (signature ID)

What it is. The rule's numeric identifier, shown as [gid:sid:rev]. In the system. A duplicate SID makes the probe drop rules silently. To find duplicates: grep -oh 'sid:[0-9]*' <rules> | sort | uniq -d. On screen. Only for managers and the superuser (#49).

#ET Open ET Open

What it is. The public Emerging Threats ruleset. Suricata uses a subset of it (about 23 thousand rules), updated every 24 h. In the system. In observe mode (the default), every ET rule is lowered to priority 3: it appears in fast.log but doesn't reach the backend. In enforce mode, each rule keeps its original priority.

#Notice (Zeek) Notice

What it is. A Zeek detection, with a note (e.g. PortScan::Aggressive_Port_Scan) and a msg. In the system. It becomes an alert like the other probes' detections. Its severity comes from the ZEEK_NOTE_SEVERITY table.

#SIMIR SIMIR

What it is. The upstream project the Zeek scripts come from. It defines the SIMIR module, which standardizes notice messages.

#Priority Prioridade

What it is. The priority field of a Snort/Suricata rule: 1, 2, 3… It is not severity, but it determines severity (see below). The agent doesn't send alerts with priority above IDS_PUSH_MAX_PRIORITY (2).

#Severity Severidade

What it is. How serious an alert is, in four levels: Critical, High, Medium, Low (Crítica, Alta, Média, Baixa). Severe (Graves) = Critical + High. How it's computed (ids_severity.py, the same file in the agent and the backend):

  • Snort/Suricata: priority 1 is Critical. Priority 2 is Medium, or High if the message mentions scan, flood, DoS, brute force, injection, malware, exploit or nmap. Priority 3 and above is Low.
  • Zeek: by the note table (ZEEK_NOTE_SEVERITY), then by prefix, then by a [LOW], [MEDIUM], [HIGH] or [CRITICAL] tag in the message; if nothing matches, Low.

What it does in the system. Decides whether the alert goes up and whether it blocks (see Automatic block). On screen, each level has its own color (#64). Avoid seriousness and criticality.

#Alert Alerta

What it is. One detection by one probe about one source → destination pair. It is stored in suricata_alerts, snort_alerts or zeek_alerts, with signature, SID, severity, IPs, ports and protocol. In the system. The agent aggregates identical repeats and sends a summary with count, so one alert can stand for several occurrences (ocorrências).

#Incident Incidente decided

What it is. The grouping the Incidents screen shows and the manager handles: alerts with the same probe, signature, severity, source and destination. What it does in the system. It is the unit of handling. Handle, False positive and Reopen act on the group (POST /api/incidents/ack). A new occurrence reopens the incident. Note. In the database, the incidents table (Incident) is the legacy Zeek flow, with other statuses (new, investigating…, of which only new and resolved are used). The on-screen incident is not that table. Decided: the legacy table is migrated to the alert model. Text rule. Incident for the group, alert for each detection, occurrence for each repeat. Today the Incidents screen talks about "alerts from all three engines" and the button says "Handle alert". Related: #10 and #64.

#Incident status Situação do incidente

en pt In the code Meaning
Open Em aberto ack_status = NULL nobody has handled it yet
Handled Tratado resolved the manager saw it and acted
False positive Falso positivo false_positive the traffic was legitimate

Actions: Handle / Tratar, Mark as false positive / Marcar como falso positivo, Reopen / Reabrir. Avoid resolved on screen, which collides with appeals.

#False positive Falso positivo

What it is. Legitimate traffic that matched a rule: DNS heuristics, phone photo backups, SYN bursts to a CDN. In the system. It is also the status a manager sets on an incident. Today, setting it doesn't change the rule or undo the block. Related: #6 and #11.

#k-of-n (majority vote) k de n (votação por maioria)

What it is. An alert agent policy: a Critical or High alert goes up to the backend only when at least k of the n probes (default 2 of 3, IDS_MAJORITY_K) flag the same source IP within 20 s (IDS_MAJORITY_WINDOW). Why it exists. It reduces false positives (the group's SBSeg 2026 paper; #18). Decided: the agent's behavior applies. Medium and Low alerts don't go up to the backend; only Critical and High alerts confirmed by k probes do. The backend's Medium correlation (below) stays inactive: it only runs with IDS_MAJORITY_K=0, which is not the stack's configuration. The docs that describe the Medium path as active (how-to-test) need to be fixed.

#Aggregation Agregação

What it is. The agent merges identical alerts (probe, SID, source, destination): it sends the first one at once and a summary every 30 s (IDS_AGGREGATE_WINDOW). Not to be confused with grouping into an incident, which the screen does. Note. The screen shows the agent's summary as one row: it counts database rows and doesn't add up the summary's count.

#Automatic block Bloqueio automático

What it is. A block the backend applies based on alerts. How it decides (incident_service.py):

  • High or Critical severity (already confirmed by k probes in the agent): blocks at once.
  • Medium severity: with the stack's configuration, it doesn't reach the backend and doesn't block (see k-of-n). With IDS_MAJORITY_K=0, the backend would block by correlation on the same IP within a 60 s window: either diversity (3 distinct signatures, IDS_AUTOBLOCK_DISTINCT_SIGNATURES) or persistence (20 occurrences spread over at least 15 s; IDS_AUTOBLOCK_REPEAT_COUNT, IDS_AUTOBLOCK_REPEAT_MIN_SPAN_SECONDS, IDS_AUTOBLOCK_REPEAT_WINDOW_SECONDS).
  • Low severity: never blocks.
  • IPs in IDS_AUTOBLOCK_WHITELIST (the allowlist) are never blocked. The same IP isn't blocked twice within IDS_AUTOBLOCK_DEDUP_TTL (300 s). That memory lives in the backend process and is not cleared when the manager allows the device again.

The device is matched by IP within the alert's unit. Stored reason. Today it reads "Bloqueio automático (suricata) - Suricata 1234: ", where 1234 is the alert's database id (not the SID). Decided (#49): the user sees only what was detected, without the probe and that number. On main as of 2026-10-19 the user still sees both; the fix is in PRs _backend#8 and _frontend#7. Avoid "Administrative block" for the automatic one: the automatic feedback row uses that text and confuses readers.

#Auto-block allowlist Lista de exceção do bloqueio

What it is. IDS_AUTOBLOCK_WHITELIST: source IPs the IDS never block (CIDR accepted). It should hold at least the IoTEdu gateway, the VLAN router and the DNS servers. The default is empty; implanta.sh configurar suggests the router and LAN_IP, and verificar warns if they're missing. Avoid whitelist and blacklist in new text; use allowlist. The variable name stays.

6 Alert delivery (agent and credential)

#Alert agent Agente de alertas decided (#42)

What it is. The iotedu-ids-push-agent container (component ids-agent). What it does in the system. One thread per probe reads the alert file:

  • Suricata: fast.log;
  • Snort: alert_fast.txt;
  • Zeek: notice.log.

The agent then:

  1. computes severity;
  2. applies k-of-n and aggregation;
  3. sends signed batches to POST /api/ids/events;
  4. sends a heartbeat (POST /api/ids/heartbeat) with each probe's state.

If a probe's thread dies, nothing restarts it (#25). Today it is called: "push agent", "agente push", "IDS sensor", "push sensor". Decided. Alert agent / Agente de alertas on screen, and "push agent" only in technical docs.

#Agent credential Credencial do agente decided

What it is. The public UUID + secret pair that identifies an alert agent to the backend. It lives in the ids_sources table (IdsSource) and belongs to a unit. What it does in the system. Every request carries X-IDS-Source-ID and an HMAC-SHA256 signature of the body, with a 300 s clock tolerance. The backend checks the signature against the secret, which is stored encrypted. db-init writes the deployment's credential to agent.env. The superuser creates and disables credentials; the superuser and the unit's manager rotate the secret, which is shown only once. The screen currently calls it "IDS sensors", and the list shows "Engine: mixed". Decided. The screen becomes Alert agents / Agentes de alertas, and mixed becomes All probes / Todas as sondas. Note. The name sensor_type means the probe in an event but mixed on a credential.

#Heartbeat Sinal de vida

What it is. The agent's periodic message. It updates last_seen_at and engines_status (e.g. {"suricata":true,"snort":false,"zeek":true}). In the system. The agent sends one every 60 s (IDS_HEARTBEAT_INTERVAL) and as soon as a probe changes state. A probe counts as up while its .engine_alive is less than 90 s old (IDS_ENGINE_FRESH_SECONDS). The agent counts as online if it spoke in the last 5 min; the map uses 15 min. These two thresholds need to be unified. Note. The heartbeat says whether the probe is running, not whether the agent is reading its file (#25).

#SSE (legacy) SSE (legado)

What it is. The old mode, in which the backend pulled alerts from the IDS host (/api/scanners/*/sse/alerts). Not part of the current flow. Note. GET /api/incidents/stream is also SSE, but it is something else: the real-time notice of a new incident sent to the dashboard.

#Sign-in method Método de login

What it is. Each way of signing in: CAFe, Google and IoTEdu IdP. What it does in the system. The superuser turns each method on or off (platform_settings['login_methods']). #Sign in, Sign out Entrar, Sair

#IdP IdP (identity provider)

10 Fingerprint

#Fingerprint Fingerprint

What it is. The fingerprint component (container iotedu-fingerprint). Its name is Fingerprint in English and Portuguese; avoid IoT-ID, device fingerprinting and device identification as alternative names. What it does in the system. Listens to DHCP requests on the IoT network and characterizes each new MAC (DHCP options, UPnP, TCP stack). During self-registration it suggests name, type, manufacturer and model. The result is stored on the device as fingerprint_sha256. The Fingerprints screen was removed from the menu.

#Risk (fingerprint) Risco

What it is. The fingerprints screen's classification: Safe, Monitor, Vulnerable (Seguro, Monitorar, Vulnerável). Note. Monitor is already the name of the "Acompanhar" menu group. If the screen comes back, use Watch.

#Compose profile Perfil (do compose)

What it is. An optional set of services: ids (probes and agent), clients (synthetic clients), monitoring. Note. In Portuguese, Perfil is also the Meu perfil screen. In the docs, always write "compose profile".

#Caddy (reverse proxy) Caddy (proxy)

What it is. The reverse proxy iotedu-app-proxy (configured in bootstrap). It terminates TLS for the three domains (APP_DOMAIN, API_DOMAIN, IDP_DOMAIN).

#Monitoring Monitoramento

What it is. The monitoring component: cAdvisor → Prometheus → Grafana, with CPU, memory and network usage per container. It is not System health: that one says whether each service responds and shows a current snapshot of CPU and memory (Dozzle); Monitoring keeps historical series (Prometheus/Grafana).

#Dozzle Dozzle

What it is. The container log viewer (127.0.0.1:11080). It is outside the monitoring profile, despite the name iotedu-monitor-dozzle. In the system. Since #55 it is also the source of System health telemetry (CPU, memory, version): the backend follows its event stream (DOZZLE_INTERNAL_URL). That's why its version is pinned in DOZZLE_TAG. The dashboard has no link to Dozzle.

#Synthetic clients Clientes sintéticos

What it is. The clients component: two containers (iotedu-gw-client1/2) that request DHCP like a device does, to validate DHCP and the firewall. They are not simulated IoT devices. The component also holds the physical VLAN override.

#AttackZoo AttackZoo

What it is. The attack component: a catalog of 60 attack containers (reconnaissance, L2/L3, web, brute force, tunneling, DoS, IoT protocols) and 9 target servers, for testing the IDS. It is outside the main compose and is run by hand.

#Gateway state Estado do gateway

What it is. The reservations, firewall groups and leases, stored on the iotedu_gateway_state and iotedu_gateway_leases volumes. Note. The database and the gateway can diverge (the dashboard says Allowed, but the IP isn't in the group). recriar-tudo compares the two at the end.
