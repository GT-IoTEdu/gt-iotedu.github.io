IoTEdu multi-tenant: uma instância PostgreSQL, um schema por instituição

Uma aplicação atende todas as instituições. Cada uma tem o próprio schema e o próprio papel no banco, e o endereço acessado (unipampa.iotedu.org) decide qual schema responde. Na instituição continuam o gateway e as sondas, que agora só abrem conexões de saída.

Base: análise técnica e comparação de abordagens do GT, apresentação de 30/09 e as sugestões de Gustavo Satheler na conversa gravada no mesmo dia. Pensado para uma equipe de alunos, ainda pouco experiente em sistemas cloud native.

1 instânciaAmazon RDS for PostgreSQL 17, em São Paulo
1 schema e 1 papelpor instituição; o banco recusa acesso a outro schema
Tenant pelo hostnunca por parâmetro, corpo ou escolha do usuário
US$ 200–260/mêsinfraestrutura estimada do piloto, a conferir
Visão geral

O que roda na nuvem e o que fica na instituição

As setas mostram as únicas conexões entre campus e nuvem: eventos assinados das sondas e o long-poll do gateway, ambos abertos pela instituição e recebidos pelo Caddy. A nuvem nunca abre conexão para dentro do campus. As pessoas chegam pelo navegador, no mesmo Caddy.

O mecanismo

Como uma requisição encontra a instituição certa

  1. O navegador pedehttps://unipampa.iotedu.org/api/dispositivos
  2. O host vira tenantA API consulta plataforma.tenant. Host desconhecido ou tenant suspenso recebe 404, nunca um tenant padrão.
  3. A sessão precisa ser deste tenantO cookie vale só neste host. Sessão aberta em outra instituição recebe 403.
  4. A conexão usa o papel do tenantA API conecta como tn_unipampa_app, cujo search_path já aponta para tn_unipampa. As consultas não citam schema.
  5. O banco é a última barreiraSe algum código tentar ler outro schema, o PostgreSQL responde permission denied.
-- criar-tenant ufscar "UFSCar" ufscar.iotedu.org
CREATE ROLE tn_ufscar_app LOGIN NOINHERIT PASSWORD '…';
ALTER ROLE tn_ufscar_app SET search_path = tn_ufscar;
CREATE SCHEMA tn_ufscar;
-- alembic upgrade head, dentro de tn_ufscar
GRANT USAGE ON SCHEMA tn_ufscar TO tn_ufscar_app;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA tn_ufscar TO tn_ufscar_app;

-- conectado como tn_ufscar_app:
SELECT * FROM dispositivo;             -- os da UFSCar
SELECT * FROM tn_unipampa.dispositivo;
ERROR:  permission denied for schema tn_unipampa

Decisões arquiteturais

Doze decisões, cada uma com o gatilho para rever

ADR-001dados

Uma instância Amazon RDS for PostgreSQL 17

Decisão
Single-AZ no piloto; Multi-AZ com o primeiro cliente pagante. Backup e atualização com o provedor.
Descartadas
MySQL; um banco por cliente; PostgreSQL em contêiner operado pela equipe
Rever quando
CPU do banco acima de 60% em horário letivo ou mais de ~150 tenants
ADR-002dados

Um schema e um papel de banco por tenant

Decisão
search_path fixo no papel; tabelas sem tenant_id; o papel só tem permissão no próprio schema.
Descartadas
Pool com tenant_id e RLS; banco por cliente
Rever quando
Centenas de tenants, ou consultas entre tenants se tornarem frequentes
ADR-003dados

Tenant resolvido pelo host

Decisão
Consulta a plataforma.tenant; sessão presa ao host; host desconhecido recebe 404.
Descartadas
Tenant em parâmetro, cabeçalho, corpo ou escolhido pelo usuário (como o ?institution_id= de hoje)
Rever quando
Não se aplica
ADR-004dados

Alembic por schema e entrada de tenant por comando

Decisão
As mesmas migrações rodam em cada schema; criar-tenant cria papel, schema, tabelas e registro; migrações compatíveis com a versão anterior do código.
Descartadas
Migração manual (setup_database.py); um repositório de migração por cliente
Rever quando
Migrar todos os schemas passar de ~10 minutos
ADR-005infraestrutura

AWS Secrets Manager para credenciais

Decisão
Senha de cada papel e chaves HMAC no cofre; arquivo local só em desenvolvimento.
Descartadas
Variável de ambiente; segredo em texto puro no banco (como hoje)
Rever quando
Não se aplica
ADR-006borda e eventos

Fila no próprio PostgreSQL

Decisão
FOR UPDATE SKIP LOCKED para a fila e LISTEN/NOTIFY para o painel em tempo real; gravação idempotente por id_externo.
Descartadas
Kafka, RabbitMQ, SQS, MQTT
Rever quando
Mais de ~500 eventos/s sustentados ou atraso de fila acima de 5 s
ADR-007borda e eventos

Backend decide o bloqueio; gateway busca a lista

Decisão
Long-poll HTTPS com HMAC; lista versionada e assinada com tenant e gateway; gwapi só em localhost.
Descartadas
Nuvem chamando o gateway (como hoje); MQTT ou IoT Core; decisão na borda
Rever quando
Latência medida acima da meta, ou exigência de bloqueio sem nuvem
ADR-008identidade

Login central com CAFe e Google

Decisão
Um SP e um cliente OAuth em login.iotedu.org; código de uso único devolve a pessoa ao host do tenant; pertinência por convite, IdP ou domínio.
Descartadas
Keycloak broker desde já; Cognito; um SP por tenant
Rever quando
Primeiro cliente fora da CAFe e do Google
ADR-009dados

Um pool de conexões pequeno por tenant

Decisão
2 a 5 conexões por tenant, criadas sob demanda.
Descartadas
PgBouncer; SET LOCAL ROLE com pool único
Rever quando
Conexões totais perto do limite da instância RDS
ADR-010infraestrutura

Uma VM EC2 com Docker Compose

Decisão
Imagens no GHCR, deploy pelo GitHub Actions, infraestrutura descrita em OpenTofu.
Descartadas
ECS Fargate; Kubernetes; VPS fora da AWS
Rever quando
Precisar de mais de uma VM ou de deploy sem interrupção
ADR-011infraestrutura

Caddy na borda

Decisão
Certificado curinga por desafio DNS e TLS sob demanda para domínio próprio, autorizado pelo registro de tenants.
Descartadas
ALB, CloudFront e ACM
Rever quando
Centenas de domínios próprios ou exigência de WAF gerenciado
ADR-012infraestrutura

AWS em São Paulo

Decisão
Provedor do MVP, com pedido de créditos para startups (AWS Activate); peças portáveis (contêiner, PostgreSQL, API S3).
Descartadas
Google Cloud, Azure, Kubernetes independente de provedor
Rever quando
Créditos, contrato da RNP ou custo mudarem a conta

Riscos

O que pode dar errado, e o que segura

RiscoMitigação
A aplicação envia a origem erradaTenant resolvido num único lugar; sessão presa ao host; papel sem acesso a outros schemas; suíte de vazamento no CI
Credencial de um papel vazaO dano fica em um tenant; rotação pelo Secrets Manager
Muitos pools de conexãoPools pequenos; troca por PgBouncer ou SET LOCAL ROLE antes do limite (ADR-009)
Migração falha no meio dos schemasMigrações compatíveis com a versão anterior; comando idempotente que retoma de onde parou
A VM caiRecriação por OpenTofu; o gateway mantém a última lista; Multi-AZ no banco com o primeiro pagante
Plataforma comprometida envia bloqueio em massaLista assinada com tenant e gateway; o agente recusa o que não for dele e limita mudanças por versão
Equipe sem experiência de operaçãoServiços gerenciados, poucas peças, tudo em código, runbooks e revisão sênior nos marcos
Projeto de referência

O isolamento já foi testado

11/11
testes da suíte de isolamento passaram contra um PostgreSQL 16 real Dispositivo de um tenant não aparece no outro; o papel do banco não lê outro schema nem a plataforma; sessão de uma instituição não vale no host da outra; host desconhecido não cai em tenant padrão; evento vai para o tenant da credencial e reentrega não duplica; toda rota de dados usa a sessão do tenant. Na verificação de mutação, dar de propósito a um papel permissão no schema de outro fez o teste do banco falhar, como deveria. O compose e o CI foram escritos, mas não executados nesta máquina.
